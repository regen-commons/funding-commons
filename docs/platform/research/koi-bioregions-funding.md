## A. KOI (Knowledge Organization Infrastructure) — Metagov, BlockScience/Dynamical Systems Group, RMIT

### A.1 Name, lineage, who is behind it

- **Acronym.** KOI = **Knowledge Organization Infrastructure** (BlockScience/DSG and the PyPI package), spelled "Knowledge Organisation Infrastructure" in Metagov/RMIT (Australian) texts ([Metagov project page](https://metagov.org/projects/koi-pond/project-details), [koi index repo](https://github.com/BlockScience/koi), [koi-net on PyPI](https://pypi.org/project/koi-net/)). KOI-net expands to "Knowledge Organization Infrastructure Network" ([PyPI](https://pypi.org/project/koi-net/)). Two variants you may encounter are not canonical: a researchseminars.org listing expands it as "Knowledge Organization Object Infrastructure" ([researchseminars](https://researchseminars.org/talk/Metagov/218/)), and a Gaia AI meeting transcript renders it "Knowledge Object Interface" ([HackMD transcript](https://hackmd.io/@linuxiscool/S1hLS78Kgg)); both appear to be transcription/listing errors **[inference]**.
- **RID expansion.** Official sources expand RID as **Reference Identifier**, not "Resource Identifier": the rid-lib README opens "Reference Identifiers (RIDs) identify references to resources primarily for usage within Knowledge Organization Infrastructure (KOI)" ([rid-lib JSON/README on PyPI](https://pypi.org/pypi/rid-lib/json)), and Metagov's FAQ says the same ([Metagov FAQ](https://metagov.org/projects/koi-pond/faq)). The Regen Network forum post calls them "Resource Identifier" ([Regen forum](https://forum.regen.network/t/regen-koi-mcp-the-knowledge-brain-of-regeneration/561)); treat that as a secondary-source slip. ORN = **Object Reference Name** (`orn:<namespace>:<reference>`), the former RID v2 style now implemented under an unofficial `orn:` URI scheme ([rid-lib README](https://pypi.org/pypi/rid-lib/json)).
- **Organizations.** The index repo describes KOI as "a collective research effort across Dynamical Systems Group, Metagov, and RMIT" ([koi index](https://github.com/BlockScience/koi)). **BlockScience has been renamed Dynamical Systems Group (DSG)**: Michael Zargham's CV lists him as "CEO and Chief Engineer, Dynamical Systems Group (formerly BlockScience)" ([CV](https://michael.zargham.org/cv.pdf)); the GitHub organization `BlockScience` now redirects to `DynamicalSystemsGroup` (e.g. the koi-net README links `github.com/DynamicalSystemsGroup/rid-lib`), and PyPI metadata carries "Copyright (c) 2025 Dynamical Systems Group" with maintainer emails at dynamicalsystemsgroup.com ([koi-net PyPI JSON](https://pypi.org/pypi/koi-net/json), [koi-net GitHub](https://github.com/BlockScience/koi-net)). BlockScience's Q3 2025 newsletter (13 Oct 2025) still used the BlockScience name and announced no rename ([Q3 newsletter](https://blog.block.science/q3-newsletter-2025/)), so the rename happened between Oct 2025 and mid-2026 **[inference]**. The DSG site describes "a systems engineering firm founded by Dr. Michael Zargham... since 2017" ([dynamicalsystemsgroup.com](https://www.dynamicalsystemsgroup.com/)). For grant and partnership outreach, use "Dynamical Systems Group (formerly BlockScience)".
- **Version lineage** ([koi index](https://github.com/BlockScience/koi)):
  - v1 "KMS" (DSG's internal Knowledge Management System, pre-RID; KMS-GPT Slack bot; some repos private).
  - v2 "KOI Pond" (Metagov): a monolithic `koi-api` with RID v2, graph + cache + vectorstore subsystems; sensors in `kms-tools`; Neo4j graph DB; a `@KOI-GPT` Slack bot ([Metagov FAQ](https://metagov.org/projects/koi-pond/faq), [Metagov details](https://metagov.org/projects/koi-pond/project-details)).
  - v3 "KOI-net" (current; DSG + RMIT via the Telescope project): the KOI-net protocol, `koi-net` library, `koi-net-node-template`, `rid-lib`, `rid-registry`.

### A.3 Core concepts (RIDs, manifests, bundles, cache)

From the rid-lib README (RID v3 Protocol) ([rid-lib README](https://pypi.org/pypi/rid-lib/json)):

- **RID syntax**: `<type>:<reference>`; all URIs are valid RIDs (for `http`/`https` the scheme is the type and the rest is the reference). ORNs: `orn:<namespace>:<reference>`, e.g. `orn:slack.message:TA2E6KPK3/C07BKQX0EVC/1721669683.087619`. RIDs "are not intended to have universal agreement or a centralized management structure"; names ("what") vs locators ("where").
- **RID types are first-class**: `RIDType` metaclass; unknown types still parse with an auto-generated minimal class; Pydantic-compatible.
- **Manifest** (Pydantic): `rid`, `timestamp`, `sha256_hash` — all required; `Manifest.generate(rid, data)`.
- **Bundle**: `manifest` + `contents: dict`; "the construct used to transfer and store the RIDed knowledge objects".
- **Cache**: one JSON file per bundle, filename = base64 of the RID; `write/read/exists/list_rids/delete/drop`.
- **rid-registry** currently lists 13 active types: `http`, `https`, `orn:koi-net.node` (`<name>+<hash>`), `orn:koi-net.edge` (`<id>`), `orn:slack.workspace|channel|message|user`, `hackmd.team`, `orn:discord.guild|channel|message|user`; proposed `hackmd.user`. Registering a type = adding a row to the table (format acknowledged as provisional) ([rid-registry](https://github.com/DynamicalSystemsGroup/rid-registry)).

### A.4 KOI-net protocol: nodes, events, edges

- **Nodes** are "autonomous units that take in, process, and output knowledge; they nest, so a whole network can act as a node in a larger one" ([Metagov FAQ](https://metagov.org/projects/koi-pond/faq)). The framework "supports full nodes, which act as web servers exposing the protocol's endpoints, and partial nodes, which only state their type and any event types they offer" ([PyPI](https://pypi.org/project/koi-net/)). Regen's implementers summarize: "Full nodes receive webhooks; partial nodes poll" and classify roles as **sensors** (observe external sources), **processors** (transform), **coordinators** (route; keep node registry, heartbeats), **actuators** (push outward) ([Regen forum](https://forum.regen.network/t/regen-koi-mcp-the-knowledge-brain-of-regeneration/561)).
- **Events**: the "FUN" triad **NEW** (never-seen knowledge), **UPDATE** (changed; new version distributed), **FORGET** (item lapsed; nodes drop it) ([Regen forum](https://forum.regen.network/t/regen-koi-mcp-the-knowledge-brain-of-regeneration/561)); Metagov describes nodes sending "notices when knowledge is added, edited, or removed" ([Metagov details](https://metagov.org/projects/koi-pond/project-details)).
- **Knowledge-processing pipeline** (Regen's description of the koi-net design): five phases — RID, Manifest, Bundle, Network, Final — with handlers at each stage that can inspect/modify/enrich/halt; e.g. an RID handler drops events about the node itself to avoid loops ([Regen forum](https://forum.regen.network/t/regen-koi-mcp-the-knowledge-brain-of-regeneration/561)). The node template ships a `custom_handler.py` example and tells you to declare the RID types your node handles in `config.py` ([node template](https://github.com/DynamicalSystemsGroup/koi-net-node-template)).
- **Network graph / edges**: a directed graph of providers and subscribers; edges negotiated by type (Provider/Subscriber), RID filter and capabilities ([Regen forum](https://forum.regen.network/t/regen-koi-mcp-the-knowledge-brain-of-regeneration/561)); `orn:koi-net.node` and `orn:koi-net.edge` are themselves RID types ([rid-registry](https://github.com/DynamicalSystemsGroup/rid-registry)).
- **Coordinator / first contact**: `koi-net-coordinator-node` is the "Coordinator node for local KOI-net bootstrap and network graph state"; other nodes default `first_contact` to `http://127.0.0.1:8080/koi-net`; each node holds a private key protected by `PRIV_KEY_PASSWORD`, auto-writes `config.yaml` on first run; Dockerfile and systemd unit provided ([coordinator node](https://github.com/DynamicalSystemsGroup/koi-net-coordinator-node)). The 2.x protocol upgrade adds cryptographic node-to-node verification ("nodes verify each other cryptographically, enabling cross-org sharing") ([HackMD transcript](https://hackmd.io/@linuxiscool/S1hLS78Kgg)); the `cryptography>=50` dependency is consistent with that ([PyPI JSON](https://pypi.org/pypi/koi-net/json)).
- **Effector / resolution**: an RID is resolved by checking cache → action (generate/fetch) → network (ask peers) ([Regen forum](https://forum.regen.network/t/regen-koi-mcp-the-knowledge-brain-of-regeneration/561)).
- **Minimal node in code**: subclass `PartialNodeConfig` with `koi_net = KoiNetConfig(node_name=..., node_profile=PartialNodeProfile(...))`, subclass `PartialNode` with `config_schema`, call `.run()`; base node classes assemble ~36 dependency-injected components; see `examples/coordinator.py` ([PyPI](https://pypi.org/project/koi-net/)).
- **The protocol as specified — "KOI-net Protocol Specification Draft v1.0"** ([spec draft](https://dynamicalsystemsgroup.github.io/koi-net-spec/v1.0-draft-release.html)):
  - *Node types.* A **full node** runs a server and a client, supports all five API methods, lets others fetch its state and receives events by webhook at `/events/broadcast`; a **partial node** is client-only, cannot be fetched from, receives events only by polling full nodes, and sends events only to full nodes. Partial nodes "suit setups where hosting a server is impractical or unneeded, such as app plugins or browser apps". `base_url` is required for full nodes (should end in `/koi-net`, no trailing slash) and omitted for partial nodes.
  - *Node profile* fields: `node_type` (`FULL`|`PARTIAL`), `base_url`, `provides.event` and `provides.state` (arrays of RID types; may be empty), `public_key` (SPKI DER, Base64). Node RID = `orn:koi-net.node:<name>+<hash>` where `<hash>` is the SHA-256 hex of the public key; a key change means a new RID. Edge RID = `orn:koi-net.edge:<hash>` (SHA-256 of source RID + target RID).
  - *Manifest*: `rid`, `timestamp` (ISO 8601, UTC preferred), `sha256_hash` (hex SHA-256 of the data; JSON canonicalized per RFC 8785 before hashing); extra fields allowed. *Bundle*: `manifest` + `contents` (JSON object).
  - *Event*: required `rid`, `event_type` ∈ {`NEW`, `UPDATE`, `FORGET`} (the "FUN" events); optional `manifest`, `contents`. `FORGET` should carry only the `rid`; `NEW`/`UPDATE` should carry a bundle, or manifest-only if the object is large ("lazy dereference": validate, decide, then fetch). "Events are signals, not commands."
  - *Edges*: edge profile = `edge_type` (`WEBHOOK`|`POLL`), `source` (publisher), `target` (subscriber), `status` (`PROPOSED`|`APPROVED`), `rid_types`. Negotiation is subscriber-initiated: subscriber sends a `NEW`/`UPDATE` event with a `PROPOSED` edge profile; publisher approves by returning it `APPROVED`, or rejects with `FORGET`. Partial subscribers must use `POLL`; full subscribers should use `WEBHOOK`. Allowed delivery: full→full webhook (polling "NOT RECOMMENDED"), partial→full webhook, full→partial polling, partial→partial none.
  - *HTTP API*: all methods are `POST` with JSON bodies, relative to the base URL, HTTPS required on public networks: `/events/broadcast` (`events_payload`), `/events/poll` (`poll_events`, optional `limit`), `/rids/fetch` (`fetch_rids`, optional `rid_types`), `/manifests/fetch` (`fetch_manifests`, `rids` or `rid_types`; response includes `manifests`, `not_found`), `/bundles/fetch` (`fetch_bundles`, `rids`; response includes `bundles`, `not_found`, `deferred`). 200 on success, 400 on error.
  - *Identity & signing*: each node holds an **ECDSA P-256 (SECP256R1)** key pair. Requests and non-empty responses are wrapped in envelopes `{payload, source_node, target_node, signature}`; the unsigned envelope is serialized as compact JSON, UTF-8 encoded, signed with ECDSA/SHA-256, signature encoded as raw `r||s` then Base64. Receivers verify the sender's public key hashes to its RID, the signature validates, and `target_node` is their own RID; error types `unknown_node`, `invalid_key`, `invalid_signature`, `invalid_target`.
  - *Handshake / first contact*: the initiator must already know the responder's RID and URL (a preconfigured "first contact"); it sends its own node-profile bundle as a `NEW` event; the responder may reply with its own profile. An unknown sender is accepted only on `/events/broadcast` when one event is a `NEW` bundle of the sender's own profile that passes the key/RID check. The spec defines **no coordinator role** — "coordinator" is just a conventional node name; the `koi-net-coordinator-node` repo is the reference bootstrap node.
  - *Versioning/licence*: only the title "Draft v1.0"; no protocol version field or negotiation yet. The draft contains internal inconsistencies (edge source/target field rules in §5.2 contradict §3.2; a `WEBOOK`/`PARTIAL` typo; unspecified JSON key ordering for signing) — expect breaking changes and pin to the Python reference behaviour when in doubt.

### A.5 "KOI Pond" (Metagov's instance) and Telescope consent workflow

- **KOI Pond**: Metagov's deployment pairs a KMS with RIDs in a Neo4j graph of knowledge objects ↔ members ↔ collectives; `@KOI-GPT` in Metagov Slack; by default only four Slack channels (#govbase-labs, #koi-pond, #board, #attentionecon) are observed, pre-28 Aug 2024 messages only with explicit consent; members opt out via a "Data Export Consent" profile setting; the backend stores references + metadata, not copies; only the lead developer (Luke Miller) holds backend keys ([Metagov FAQ](https://metagov.org/projects/koi-pond/faq)). The name riffs on "data pond", Ostrom, and fish swarms ([Metagov details](https://metagov.org/projects/koi-pond/project-details)).
- **Telescope** (consent workflow): "Telescope, a 2022 bot from a Metagov working group, lets researchers and members flag posts for ethnography. A flag triggers an automatic consent request and data capture; if the author approves, the post goes into a research archive" ([Metagov FAQ](https://metagov.org/projects/koi-pond/faq)). Flagging is by reacting with the telescope emoji; Telescope + KOI "tag and route insights using reference identifiers, so labels can circulate while the underlying data stays locally controlled"; approved posts flow via an RMIT KOI instance into Obsidian (plugin by Luke Miller) for ADM+S researchers; KOI node data access is restricted to key holders ([BlockScience Q3 2025 newsletter](https://blog.block.science/q3-newsletter-2025/), [Metagov FAQ](https://metagov.org/projects/koi-pond/faq)). The repo `metagov/slack-telescope` ("KOI-net Slack Telescope Node", MIT, 135 commits) is described in the index as a "consent-based ethnographic research tool… standalone 'KOI-lite' with cache and limited graph features" ([slack-telescope](https://github.com/metagov/slack-telescope), [koi index](https://github.com/BlockScience/koi)).
- **The blog post you asked for**: Ellie Rennie, "Telescope and KOI in Action: Building Feedback Loops for Organisational Intelligence", BlockScience blog, 22 Sep 2025 (first on Medium 11 Sep 2025; credits Zargham, Luke Miller, David Sisson, Elianna DeSota; RMIT/ADM+S node: Rennie, Matthew Green, Kelsie Nabben, Brooke Ann Coco; theory lead Jason Potts) — [blog.block.science](https://blog.block.science/building-feedback-loops-telescope-koi/) and Medium mirror [medium.com/block-science/...aca5ecbb5618](https://medium.com/block-science/building-feedback-loops-for-organisational-intelligence-telescope-and-koi-in-action-aca5ecbb5618). Key content: Telescope began as a Discord tool for Metagov researchers studying onchain communities and now runs on Slack too; the consent workflow is (1) a member reacts 🔭 to a message, (2) Telescope DMs the author a project summary and asks for consent, (3) on consent the message enters the dataset and appears in an approved-content channel — "without consent, nothing is saved"; in the organisation-run variant a moderator first approves the bot sending requests. The Telescope KOI node forwards only approved messages to researchers' Obsidian vaults and withholds unapproved items; RIDs act as "library-style labels" — "the labels travel but the material stays where it is"; only key-holders can access node data. Deny/anonymize/retract steps are not described (the protocol's `FORGET` exists but is not tied to consent withdrawal). The post sketches a five-stage trajectory: consent as baseline oversight → community-set policies for the sensor node (e.g. sharing some insights with a DAO alliance) → member-led analysis with traceable auto-generated insights → Telescope as a "contribution system" → KOI context constraining autonomous agents ([Telescope post](https://blog.block.science/building-feedback-loops-telescope-koi/)). The Q3 newsletter adds: communities can define rules, trace provenance, and pass vetted context to LLMs within set limits, forming "real-time loops running from observation to action" ([Q3 newsletter](https://blog.block.science/q3-newsletter-2025/)). Companion reading: "A Preview of the KOI-net Protocol" and "KOI Nodes as Neurons" (BlockScience blog, cited by Regen) ([Regen forum](https://forum.regen.network/t/regen-koi-mcp-the-knowledge-brain-of-regeneration/561)); "Objects as Reference" (Orion Reed) and "A Language for Knowledge Networks" (Zargham & Ben-Meir) ([koi index](https://github.com/BlockScience/koi)).
- **Ethnographic/research framing**: an IASC 2025 commons-conference abstract reports that introducing KOI "has also revived older commons-governance problems such as drawing group boundaries" ([IASC 2025](https://2025.iasc-commons.org/?p=8018)); a Nov 2025 AANZCA liveblog describes KOI as a federated, library-style system linking existing tools through reference identifiers, with data-commons guidelines under way ([snurb.info](https://snurb.info/node/3499)). Governance of the project is informal: BlockScience/DSG developers make most technical calls, a working group is consulted on larger design decisions ([Metagov FAQ](https://metagov.org/projects/koi-pond/faq)).

### A.8 Ontologies / knowledge graphs

- BlockScience/DSG KOI defines **no formal ontology**; its model is reference/referent ("(reference) -[means of reference]-> (referent)") plus a graph of RIDs and edges (Neo4j in KOI Pond; a `networkx` NetworkGraph of nodes/edges in koi-net) ([rid-lib README](https://pypi.org/pypi/rid-lib/json), [Metagov FAQ](https://metagov.org/projects/koi-pond/faq), [PyPI JSON](https://pypi.org/pypi/koi-net/json)). RID *types* function as a lightweight, decentralized type system ([rid-registry](https://github.com/DynamicalSystemsGroup/rid-registry)).
- The Regen/Gaia deployment layers **RDF/SPARQL (Apache Jena Fuseki)** and a property graph (Apache AGE) on top, and is exploring OWL to align with Regen Ledger's RDF data module ([Regen forum](https://forum.regen.network/t/regen-koi-mcp-the-knowledge-brain-of-regeneration/561), [HackMD transcript](https://hackmd.io/@linuxiscool/S1hLS78Kgg)). **[inference]** For your platform, the natural pattern is: RIDs for identity, JSON-LD/schema.org-style records (or Murmurations profiles) for semantics, and optional RDF export — KOI does not force an ontology on you.

### A.11 Practical minimum for a Node/TypeScript app (Vercel + Supabase) to participate

There is no official JS SDK, so participation is by **protocol compatibility** (HTTP + JSON + ECDSA P-256) and **RID discipline**. The spec itself says partial nodes are meant for "app plugins or browser apps" ([spec draft](https://dynamicalsystemsgroup.github.io/koi-net-spec/v1.0-draft-release.html)), which fits a Vercel app well. Three ascending levels **[inference, grounded in the sources above]**:

1. **Publish records as RIDs (no network code).** Mint an ORN namespace for your domain objects, e.g. `orn:regencommons.initiative:<uuid>`, `orn:regencommons.need:<uuid>`, `orn:regencommons.opportunity:<uuid>`, and propose the types to `rid-registry` (a one-row PR) ([rid-registry](https://github.com/DynamicalSystemsGroup/rid-registry)). Store `rid`, `sha256_hash` (SHA-256 of the RFC 8785-canonicalized JSON contents) and `timestamp` alongside each row in Supabase so you can emit valid Manifests `{rid, timestamp, sha256_hash}` and Bundles `{manifest, contents}` on demand ([spec draft](https://dynamicalsystemsgroup.github.io/koi-net-spec/v1.0-draft-release.html), [rid-lib README](https://pypi.org/pypi/rid-lib/json)). Also store the public URL so every object is dually addressable (ORN name + HTTPS locator, both valid RIDs). Cost: a Postgres trigger + ~50 lines of TypeScript.
2. **Be a partial node (publisher) — the practical minimum.** Generate one ECDSA P-256 key pair (Node/WebCrypto `ECDSA` with `P-256` supports SPKI export and SHA-256 signing), derive your node RID `orn:koi-net.node:regen-commons+<sha256(pubkey)>`, and keep the private key in a Vercel environment secret. Handshake once by POSTing a signed envelope to a full node's `/events/broadcast` (the "first contact", e.g. a coordinator run by Metagov or Regen/Gaia) containing a `NEW` event whose bundle is your own node profile with `node_type: "PARTIAL"` and `provides.event: ["orn:regencommons.initiative", …]`. Then, from a Supabase Database Webhook or `pg_notify` → Vercel function, POST signed `NEW`/`UPDATE`/`FORGET` events (bundle, or manifest-only for large objects) to each full node that has approved an edge with you — partial→full delivery is by *webhook*, i.e. you push to their `/events/broadcast`; anything you want *from* the network you pull on a schedule (Vercel Cron) via `/events/poll`, `/manifests/fetch` and `/bundles/fetch`, since full→partial delivery is by polling ([spec draft](https://dynamicalsystemsgroup.github.io/koi-net-spec/v1.0-draft-release.html)). You never host a server endpoint for KOI, you hold one key, and the authoritative copy stays in Supabase. Implementation surface: JSON canonicalization (RFC 8785 library), compact-JSON signing, Base64 `r||s` signature encoding, five request `type` constants. Expect to track breaking changes while the spec is "Draft v1.0".
3. **Run a full node.** Implement the five `POST` endpoints under a `base_url` ending in `/koi-net` (`/events/broadcast`, `/events/poll`, `/rids/fetch`, `/manifests/fetch`, `/bundles/fetch`) with signed envelopes and edge negotiation in TypeScript, or deploy the Python `koi-net` full node (Docker image/systemd unit patterns exist in the coordinator repo) next to Supabase (e.g. Fly.io/Railway) — Vercel's serverless model is awkward for a long-lived node that keeps network-graph state and serves state fetches **[inference]** ([coordinator node](https://github.com/DynamicalSystemsGroup/koi-net-coordinator-node)). Treat this as phase 2 after the spec stabilizes ([spec index](https://dynamicalsystemsgroup.github.io/koi-net-spec)).

Consent/decentralization alignment: mirror Telescope — only publish objects a member has explicitly marked shareable, keep the authoritative copy in Supabase, and let the KOI network carry references + hashes rather than copies ([Metagov FAQ](https://metagov.org/projects/koi-pond/faq)). Also consider dual-publishing public profiles to **Murmurations** (JSON profiles indexed by a shared index) so the records are discoverable outside KOI ([Murmurations on Open Collective](https://opencollective.com/murmurations)).

### B.2 The HydroSHEDS licence question (answered)

The premise "CC-BY 4.0 since v1.1" is **not supported** by the primary document. HydroSHEDS Technical Documentation v1.4 (April 2022; Data Version 1.1) states core data "are free for non-commercial and commercial use" and attaches **Appendix A, "HydroSHEDS Version 1 – License Agreement"**: a WWF custom licence granting development, distribution and sublicensing rights **only as part of Derivative Works** ("In no event shall Licensee license or distribute the Licensed Materials as a stand-alone product"), reserving IP to WWF, and requiring (Exhibit B) a prominent statement beginning "This product [name] incorporates data from the HydroSHEDS version 1 database which is © World Wildlife Fund, Inc. (2006-2022) and has been used herein under license…" plus the Lehner, Verdin & Jarvis (2008) citation ([HydroSHEDS TechDoc v1.4](https://data.hydrosheds.org/file/technical-documentation/HydroSHEDS_TechDoc_v1_4.pdf)). HydroBASINS and HydroRIVERS explicitly inherit that agreement ([HydroBASINS TechDoc](https://data.hydrosheds.org/file/technical-documentation/HydroBASINS_TechDoc_v1c.pdf), [HydroRIVERS](https://www.hydrosheds.org/products/hydrorivers)). Only **HydroATLAS** (incl. BasinATLAS) is stated as CC BY 4.0 ([HydroATLAS](https://www.hydrosheds.org/hydroatlas)). Third-party catalogues disagree (CC BY 4.0 on one portal, CC BY-NC 3.0 on Stanford's record) ([Ponderful](https://dataportal.ponderful.eu/dataset/hydrobasins), [Stanford](https://purl.stanford.edu/zc665xv7392)); the hydrosheds.org terms page (updated May 2026) defers to per-product licences ([terms](https://www.hydrosheds.org/terms-of-use)). **Practical reading [inference]:** server-side point-in-polygon and shipping simplified derived layers inside your app is squarely "Derivative Work" use (commercial allowed) with the Exhibit B notice; do not republish raw HydroBASINS files. If you want a clean CC BY basis for the basin layer, load **BasinATLAS** instead (same geometry, CC BY 4.0, larger files).

   - `ref.bioregion` from the One Earth shapefile (185 rows; join the Datahub CSV for `realm`/`subrealm`/`biogeographic_realm`) — CC BY-NC, so keep the platform non-commercial or obtain a licence ([One Earth datasets](https://www.oneearth.org/datasets/)).
   - `ref.ecoregion` from RESOLVE 2017 (846; CC BY 4.0) — gives a finer unit and a licence-safe fallback if One Earth ever becomes a blocker ([ecoregions.appspot.com](https://ecoregions.appspot.com/)).
   - `ref.hydrobasin` for levels **3, 5, 6, 7** (HydroBASINS "standard" format; or BasinATLAS for CC BY) with `hybas_id, level, pfaf_id, next_down, main_bas, sub_area, up_area, endo, coast` — keep `MAIN_BAS` so every point also gets its "whole river basin" family ([HydroBASINS TechDoc](https://data.hydrosheds.org/file/technical-documentation/HydroBASINS_TechDoc_v1c.pdf)).
   - `ref.admin0` / `ref.admin1` from Natural Earth 1:10m (public domain) — avoid GADM (no redistribution, non-commercial) ([NE terms](https://www.naturalearthdata.com/about/terms-of-use/), [GADM licence](https://gadm.org/license.html)).
   - Optional national precision: USGS WBD HUC8/10/12 (public domain), SDAC for Canada (OGL), EU-Hydro catchments (Copernicus) — load lazily per region when users there appear.
2. **Indexing:** `ST_MakeValid`, then `ST_Subdivide(geom, 256)` into `ref.*_sub` tables with GIST indexes — subdivision turns million-vertex bioregion polygons into fast point-in-polygon checks; keep the original for display.
3. **One RPC:** `geo.locate(lon float8, lat float8) returns jsonb` doing `ST_Intersects(geom, ST_SetSRID(ST_MakePoint(lon,lat),4326))` against each layer, with a `<->` nearest-neighbour fallback within e.g. 25 km for coastal/estuary points (One Earth's marine extension to the EEZ already catches most coastal cases) ([Bioregions 2023](https://www.oneearth.org/bioregions-2023/)). Return `{bioregion:{code,name}, subrealm, realm, biogeographic_realm, ecoregion:{id,name,biome}, basins:{lev03,lev05,lev06,lev07,main_bas}, admin:{iso_a2,admin1}, dataset_versions:{…}}`. Expose via Supabase RPC (SECURITY DEFINER, read-only role) and **cache the result on the initiative row** (codes only, plus `dataset_versions` for provenance) so reads never touch geometry.
4. **Named place → point:** geocode once at entry time (user picks a suggestion on a map; store point + precision). Public Nominatim is acceptable only at ≤1 req/s with caching and an identifying User-Agent, and no autocomplete ([OSMF policy](https://operations.osmfoundation.org/policies/nominatim/)); for autocomplete use a self-hosted Photon/Pelias or a paid provider, or Who's On First for coarse place → centroid (link the licence page) ([WOF licences](https://whosonfirst.org/docs/licenses/)). Then run `geo.locate` on the point.
5. **Naming the watershed:** HydroBASINS/HydroRIVERS carry **no names** ([HydroRIVERS](https://www.hydrosheds.org/products/hydrorivers)). Options: (a) let communities label their `hybas_id` (crowdsourced, stored in your DB — a genuine commons contribution), (b) join Wikidata basin items via P4614/labels for multilingual names ([P4614](https://www.wikidata.org/wiki/Property:P4614)), (c) nearest HydroRIVERS main stem ↔ OSM `waterway` name. Store the chosen label with its source.
6. **KOI tie-in [inference]:** mint RIDs for reference units (`orn:oneearth.bioregion:NA1`, `orn:hydrobasins.lev06:7060012340`) so initiatives, needs and funding opportunities can reference the same place objects across nodes without copying geometry.
7. **Attribution block** (footer/API): One Earth citation; RESOLVE CC BY 4.0; the HydroSHEDS Exhibit B statement + Lehner et al. 2008 + Lehner & Grill 2013; "Made with Natural Earth"; © OpenStreetMap contributors (ODbL) if Nominatim/Photon is used; Copernicus wording for EU-Hydro ([HydroSHEDS TechDoc v1.4](https://data.hydrosheds.org/file/technical-documentation/HydroSHEDS_TechDoc_v1_4.pdf), [CLMS data policy](https://land.copernicus.eu/en/data-policy)).

**Estimated sizes [estimates]:** raw inputs ≈ 150 MB (RESOLVE) + ~50–150 MB (One Earth shapefile, unpublished) + ~0.5–1.5 GB (HydroBASINS levels 3–7, all regions) + ~10 MB (Natural Earth 10m); in PostGIS with subdivided copies ≈ 2–4 GB, within a Supabase Pro database. Query cost after subdivision: single-digit milliseconds per layer.

### B.5 Lightweight in-browser alternative (Turf.js)

**[Design recommendation.]** Pre-simplify with `mapshaper -simplify 2% keep-shapes` (or `-simplify interval=2000` ≈ 2 km) and export quantized TopoJSON, gzip, serve from Vercel/edge with long cache:
- Bioregions (185 polygons incl. marine extents): ≈ 1–3 MB gz; realm/subrealm derived by attribute join from the 16 kB CSV **[estimate]** ([Datahub](https://datahub.io/climate-and-environment/bioregions-2023)).
- Ecoregions (846): ≈ 4–8 MB gz **[estimate]** — load only when the user opens a detail view.
- HydroBASINS: ship **level 4 or 5 globally** (≈ 3–8 MB gz **[estimate]**) and lazy-load **level 6/7 per continent** (the data already come as 9 regional files) only for the region containing the point (≈ 2–10 MB per region **[estimate]**); or publish all levels as **PMTiles** vector tiles and use MapLibre `queryRenderedFeatures`, which avoids loading whole layers.
- Lookup: bbox pre-filter with `flatbush`/`geojson-rbush`, then `@turf/boolean-point-in-polygon`; expect boundary errors of roughly the simplification tolerance — fine for "which bioregion/basin" at level ≤6, acceptable at level 7 if you also offer a "correct this" affordance.
- Licence note: a simplified bioregion file is still One Earth data (CC BY-NC) and a simplified HydroBASINS file is a WWF Derivative Work — serve them as part of the app with the attribution block, don't offer them as standalone downloads ([One Earth datasets](https://www.oneearth.org/datasets/), [HydroSHEDS TechDoc v1.4](https://data.hydrosheds.org/file/technical-documentation/HydroSHEDS_TechDoc_v1_4.pdf)).

### B.6 Native Land Digital — terms (and whether commercial keys exist)

- Since 20 Nov 2024 every API request needs a **key** issued after signing up and accepting the **"Data Sovereignty Treaty & Agreement"**; from 1 May 2025 access was switched off for anyone who had not re-agreed; Terms of Use last updated 14 Feb 2025 ([NLD Substack](https://nativeland.substack.com/p/native-land-digital-api-indigenous)).
- **Permitted:** research and learning consistent with the treaty's principles; **non-commercial apps that bring in no revenue**; Indigenous-led projects advancing self-determination. **Prohibited:** commercial use incl. "monetized platforms, data resale, or proprietary applications"; storing or redistributing API data without express permission; altering territory boundaries without the affected communities' consent; uses that misrepresent Indigenous lands. **Required:** credit Native Land Digital and acknowledge Indigenous communities as the data's custodians. Access can be revoked; the terms are described as legally binding; contact tech@native-land.ca ([NLD Substack](https://nativeland.substack.com/p/native-land-digital-api-indigenous)). The API is still described as free; **no commercial key tier exists** — commercial use is simply disallowed **[inference from the absence of any paid tier in the terms]**.
- The older API docs page still says the dataset "can be considered CC0" and asks only for respectful use and a non-legal-boundaries disclaimer ([NLD API docs](https://api-docs.native-land.ca/about-and-disclaimers)); the FAQ bars commercial use of the *maps* ([NLD FAQ](https://native-land.ca/about/faq)). Treat the 2025 treaty as controlling **[inference]**.
- **Design consequence:** call the API live (server-side, short in-memory TTL), never persist polygons or build your own territory index, display the "not legal boundaries" disclaimer, and keep the platform non-commercial — or ask NLD in writing before caching even territory names on initiative records.
- Multilingual layers: Native Land covers territories, **languages** and treaties ([Wikipedia](https://en.wikipedia.org/wiki/Native_Land_Digital)); One Earth names are English-only; Wikidata labels are the practical multilingual source for basins and admin areas ([P4614](https://www.wikidata.org/wiki/Property:P4614)).

- **Murmurations** — "unfunded volunteer-led project"; donations via Open Collective/BTC; partner collectives pay for integrations (Ecosystem Map paid Hylo $1,500 in Jun 2023 and $5,500 in Feb 2025 to publish groups to Murmurations) ([Murmurations](https://murmurations.network/), [OC Murmurations](https://opencollective.com/murmurations), [Ecosystem Map expense](https://opencollective.com/ecosystem-map/expenses/237625)). Lesson: protocol layers do not self-fund; budget them as line items in platform grants.
- **Endowment-yield models** — Octant funds rounds from staking yield on Golem's ETH and now hosts vaults for other treasuries; Gitcoin moved $1M into such a vault to fund rounds from yield ([growthepie](https://www.growthepie.com/quick-bites/octant-v2-migration), [Gitcoin case study](https://gitcoin.co/case-studies/from-one-off-rounds-to-ongoing-impact-gitcoin-s-new-sustainable-funding-model)). **[inference]** A bioregional financing facility could underwrite the platform the same way.

### C.3 Requirements that shape the architecture

1. **Open-source licence, decided early.** NLnet, Sovereign Tech, EF ESP and OSC all require OSI/FSF-style licences; Hylo chose Apache 2.0 ([NLnet propose](https://nlnet.nl/propose), [STF fund](https://www.sovereign.tech/programs/fund), [ESP applicants](https://esp.ethereum.foundation/applicants), [OSC criteria](https://docs.oscollective.org/interested-in-joining-osc/acceptance-criteria.md), [Hylo about](https://www.hylo.com/about)).
2. **"Working technology in use" + AI as core + small/efficient/user-controlled** for Mozilla — favours on-device or small open-weight models, data minimisation, and a demonstrable pilot community before 20 Nov 2026 ([dev.to](https://dev.to/devengers/dev-opportunity-radar-23-500k-mozilla-ai-incubator-100k-kiroween-hackathon-and-wispr-flow-3h48)). Mozilla will not fund GPU/server purchases for for-profit grantees — apply as/through a nonprofit ([Mozilla eligibility PDF](https://assets.mofoprod.net/network/documents/Mozilla_Foundation_Grant_Eligibility_Guidelines_tNhKrgM.pdf)).
3. **No frontier-model dependency is formally required by any programme found**, but NLnet now requires disclosure of AI-generated code and human-written proposals, and Mozilla's principles penalise "bigger models, heavier compute, do-everything systems" ([NLnet propose](https://nlnet.nl/propose), [dev.to](https://dev.to/devengers/dev-opportunity-radar-23-500k-mozilla-ai-incubator-100k-kiroween-hackathon-and-wispr-flow-3h48)). Keep model choice pluggable (local by default, remote optional).
4. **Legal entity:** Humanity AI and most US foundations need a US 501(c)(3) or fiscal sponsor; OSC or a BFI-style sponsor (as BioFi uses) solves this ([GrantedAI](https://grantedai.com/blog/humanity-ai-10-million-open-call-live-september-10-2026-october-21-deadline-three-tiers-75000-to-1-million-lever-for-change-open-weight-preference-strategy), [BioFi](https://www.biofi.earth/)). EU NGI money needs a European dimension ([NLnet propose](https://nlnet.nl/propose)).
5. **Data sovereignty & licences constrain monetisation:** One Earth bioregions are CC BY-NC and Native Land forbids "monetized platforms" and caching ([One Earth datasets](https://www.oneearth.org/datasets/), [NLD Substack](https://nativeland.substack.com/p/native-land-digital-api-indigenous)). Paid *stewardship services* (Hylo pattern) are safer than paid platform tiers unless you swap to CC BY layers (RESOLVE, BasinATLAS) and obtain written clarification from NLD **[inference]**.
6. **Crypto rails are optional, not required:** EF pays in ETH; Octant/Gitcoin/Giveth/Celo need onchain identity; everything else is fiat. Design the funding-opportunity model to represent both.
7. **Decentralisation story sells:** KOI's "references travel, material stays" and Telescope's consent gate map directly onto Mozilla's "user control of data" and onto Hylo's "take your data with you" ([Telescope post](https://blog.block.science/building-feedback-loops-telescope-koi/), [Hylo about](https://www.hylo.com/about)).

### C.4 Suggested sequencing **[inference]**

1. **Now–20 Nov 2026:** Mozilla Human-Scale AI (if a pilot community is live and the matching/AI feature is real). 2. **Q4 2026:** apply to OSC (or confirm Regen Commons' own entity) so later awards have a rail. 3. **Q1 2027:** NLnet next window (protocol/client work), Climate Collective accelerator, Giveth/Gitcoin regen rounds for community donations. 4. **Apr 2027:** Ma Earth Round 4 as a *partner* (list its round; onboard your initiatives). 5. **2027:** Humanity AI next call (US fiscal sponsor), Sovereign Tech only if a dependency reaches adoption. Throughout: BioFi's Community of Practice and the BFF design partners as pilot bioregions.
